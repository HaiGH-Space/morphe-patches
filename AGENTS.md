# AGENTS.md

Instructions and repository conventions for AI coding agents working in `HaiGH-Space/morphe-patches`.

## Project Overview

- **Purpose:** Custom Android app patches built with Morphe Patcher, packaged as `.mpp` patch bundles for Morphe Manager / Morphe Desktop.
- **Template Origin:** Based on `MorpheApp/morphe-patches-template`.
- **License:** GNU General Public License v3.0 (`LICENSE`).
- **Naming & Attribution Rule:** Never use project names, package groups, or descriptions that imply official authorship by the Morphe open-source project (see `NOTICE`).

## Build & Local Verification

- **Build patch bundle:**

  ```bash
  ./gradlew buildAndroid

  ```

* **Output artifact:** `patches/build/libs/patches-*.mpp`
* **Local testing:** Apply the compiled `.mpp` file locally using [Morphe Desktop](https://github.com/MorpheApp/morphe-desktop).

- **Generate release signing keys (if requested):**

  ```bash
  ./gradlew generateSigningKey

  ```

- Commit `morphe-signing.pub`.
- **Never** commit `morphe-signing.key` (store its contents only in the `MORPHE_SIGNING_KEY` GitHub Actions secret).

## Key Files & Structure

- `patches/build.gradle.kts` — Project `group` (line 1) and bundle `About` metadata (lines 6–11).
- `patches/` — Source code for patches and fingerprints.
- `README.md` — User-facing documentation; patch list between `<!-- PATCHES_START EXPANDED -->` and `<!-- PATCHES_END -->` is auto-generated by CI.
- `.github/workflows/release.yml` & `.releaserc` — Automated semantic-release and bundle publishing pipeline.
- `.github/scripts/generate_patches_readme.py` — Script generating the README patch table (set `INCLUDE_APP_ICONS = True` to display app icons).
- `.github/ISSUE_TEMPLATE/` — Repository issue templates.
- `patches-bundle.png` _(optional)_ — Custom icon shown in Morphe Manager instead of the GitHub profile avatar.

## Git & Release Workflow

1. **Branching:** Make all development commits on the `dev` branch. Do not commit directly to `main`.
2. **Commit Convention:** Use Semantic Commits restricted to these 3 prefixes:

- `feat: <summary>` — New patch or user-facing feature (triggers a pre-release on `dev`).
- `fix: <summary>` — Bug or fingerprint fix (triggers a pre-release on `dev`).
- `chore: <summary>` — Internal maintenance/tooling changes (does **not** trigger a pre-release or changelog entry).

3. **Stable Releases:** Promote `dev` to `main` by **creating a Pull Request (PR) from `dev` to `main`** and merging it using a standard **merge commit only**. **Never** merge locally and push directly to `main`, and **never squash-merge** `dev` into `main`, as `semantic-release` depends on individual commit history.

## Strict Guardrails (Do Not Violate)

- **Do NOT push directly to `main` or merge locally:** Always create a Pull Request from `dev` to `main` and merge it on GitHub using a standard merge commit.
- **Do NOT manually edit or commit generated release artifacts:**
- `patches-list.json`
- `patches-bundle.json`
- `CHANGELOG.md`

- **Do NOT manually edit the auto-generated patch block in `README.md`:** Leave content inside `<!-- PATCHES_START ... -->` and `<!-- PATCHES_END -->` untouched (only remove `EXPANDED` to collapse the list, or remove both tags if switching to manual maintenance).
- **Do NOT manually create or upload GitHub Releases:** All releases must be produced automatically by `release.yml`.
- **Do NOT force-push semantic-release commits:** Rewriting history on `dev` or `main` breaks automated versioning; create a new fix commit/release instead.
- **Do NOT commit private keys:** Never stage or commit `morphe-signing.key`.
